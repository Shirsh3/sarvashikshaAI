Verdict: Strong mid-stage product. Not prod-ready yet. Fix security leaks and prove one full paid order before launch.

Business feedback

What’s working

  • Real marketplace shape: society-gated foodies + home chefs + ops/finance split.
  • Compliance-aware design: GST breakup, platform fee GST, FSSAI/GSTIN gates, night order blackout, max qty per order.
  • Ops pulse already tracks pending societies, unit assignments, and support tickets.

Risks / friction

  • Chef publish path is heavy (catalogue → credentials for some dish types → photo → time windows). Needs guided onboarding or drop-off will be high.
  • Night blackout (11:00 PM–5:00 AM) is fine as policy, but staging needs a controllable override for testing/releases.
  • Ops backlog (stale/unassigned tickets, pending assignments) will hurt trust if present at launch.
  • Revenue moment (payment → confirmed order) must be proven end-to-end before go-live confidence is high.

Technical feedback

Strengths

  • Clear API surface and role separation (foodie vs ops/finance).
  • Auth rate limits and bot protections observed working.
  • Billing integrity validated on a live cart:
    • Item subtotal matched unit × qty
    • Food GST @ 5% correct
    • Platform fee + GST @ 18% correct
    • Grand total = items + fee + GST (PASS)
  • Business rules enforced: max quantity per order, catalogue binding, image upload path validation, accepting-window vs fulfillment ordering.

Must-fix before production

  1. Critical: Captcha API must not return the plaintext answer.
  2. Critical: OTP must not be returned in API JSON (SMS/app only).
  3. High: Disable staging-only/dev tools in production.
  4. High: Rotate weak ops credentials; add MFA for admin login.
  5. Medium: Add CSP / X-Frame-Options / HSTS on the Flutter web host.
  6. Medium: Clarify cart quantity semantics (appears additive, not absolute set).

E2E product status

Proven

  1. Ops admin login & scoped access
  2. Society / unit assignment
  3. Foodie + chef profile creation
  4. Chef catalogue → meal publish (with image)
  5. Foodie browse → cart → multi-item → GST bill breakdown

Not fully proven (this pass)

  1. Payment create/confirm (blocked by night order window during test)
  2. Order visible to chef → accept → ready → pickup
  3. Refund / settlement / coupon on a real paid order
  4. Full Flutter UI journey (API-tested; not full browser click E2E)

Priority recommendations

  1. Stop returning captcha answers and OTPs in API responses.
  2. Production config lockdown (dev tools off, secrets rotated, MFA for ops).
  3. Re-run payment → order confirm after 5:01 AM IST (or add staging blackout override).
  4. Document chef onboarding (GSTIN/FSSAI/catalogue/photo/windows).
  5. Clear ops backlogs before launch.
  6. Add CI API smoke tests for cart math + authz + publish gates.
  7. Make night-window hours configurable (env/ops setting), keep UI copy in sync.

Night order window note

Orders are rejected between 11:00 PM and 5:00 AM (server-side + app banner).
This is not changeable from Ops UI today — it needs a backend/config (and matching app string) change if you want different hours or a staging override.
